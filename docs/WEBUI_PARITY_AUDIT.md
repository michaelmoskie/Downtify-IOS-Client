## Contract and authorization findings

The `downtify/auth.py` route list is first-match precedence. The explicit paired-device `CLIENT` carveouts for catalog search, chart, Finder, Similar, URL/preview, stream/file, stream/prefetch and download requests occur before later `ADMIN` rules. `tests/test_auth.py`'s client matrix verifies representative allowed methods and rejects method mismatches. Therefore, the older claim in `ANDROID_PARITY_AUDIT.md` that Similar and full-track streaming are beyond the device contract is incorrect for this pinned revision.

There is a documentation distinction: `docs/mobile-client-contract.md` §3 broadly permits web read endpoints, searching, previews and server download requests, but does not enumerate every current chart/Finder/Similar/stream/prefetch route or its payload. §5 documents library-ID streaming, not catalog `video_id` streaming. Implementation and auth tests establish that these routes are currently CLIENT-authorized; the mobile contract page should be expanded or pinned route references should accompany client work. Do not infer permission from a UI route alone.

In library-only mode, external search/discovery data is replaced with local catalog results where implemented; external URL resolution, preview, stream, prefetch and download operations are refused. The iOS client must retain the server's `library_only` capability/policy and suppress those external actions. Device-token downloads enqueue work for the paired account; resulting downloaded files appear later through library sync. Catalog/provider identifiers (`youtube_id`, Deezer IDs, source IDs) must never be used as `/api/v1` library track IDs.

| Task 5 server downloads | Submit the catalog song payload to `POST /api/download/url`; use `/api/download/batch` only for a verified list payload and `/api/download/album` for supported YouTube Music album URLs. Display server queue/progress separately from phone offline-file status. A later library sync, not the catalog ID, supplies the downloaded library track ID. |
| Task 6 Search/Discover UI | Implemented in the current iOS worktree: shared UI actions take typed catalog results, Finder details use provider IDs, provider links are explicit, and session/policy changes invalidate catalog state. Device UI does not offer listen-history deletion. |

**Core gate conclusion:** at the pinned server revision, the audited search, discovery, Similar, preview, stream and download routes are already implemented and CLIENT-authorized. No API or authorization code gap was found that warrants a core change for these features. The mobile contract documentation has a completeness gap (several route shapes are not enumerated); the iOS client implements against the audited route contracts, but a live server revision and credential-backed end-to-end run remain unverified.
