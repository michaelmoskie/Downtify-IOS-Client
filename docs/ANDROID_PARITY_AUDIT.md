## iOS connection flow implementation checks

- The iOS connection screen supports Bonjour discovery, direct server address entry, QR pairing, pairing-code entry, and capability-gated password sign-in. HTTP sign-in and pairing require an explicit acknowledgement that credentials and tokens are unencrypted.

- Physical-device checks before release: grant camera and local-network access, scan a real server QR code, verify Bonjour discovery across Wi-Fi/VLAN configurations, then revoke each permission in Settings and confirm recovery guidance. Simulator coverage cannot validate camera focus, real Bonjour network behavior, or router isolation.

## Verified settings inventory and connection gates

This inventory is from the pinned Android UI/data sources, not an inferred iOS design. The `SettingsScreen` groups controls as follows:

- **Server card:** server name (session name, falling back to `/api/server/info` name), address, connection tag (`Connected`, `Checking`, `Unreachable`, or `Different server`), version tag only when known, and signed-in username only when nonblank. `Change server` opens the sign-out confirmation; `Open web` opens the base URL. The separate Server group contains the same sign-out action. Sign-out forgets the token locally and retains the synced library; removing the phone from the server's paired-device list is a separate web action.
- **Playback:** `Normalize volume` toggle; when on, `Playback level` offers Normal/Louder/Maximum. Wi-Fi quality always offers Original plus supported curated transcoding choices. Mobile-data quality uses the same list and is disabled with explanatory no-transcoding text when `capabilities.transcoding.available` is false. Android proposes Opus 96/128/160/256, AAC 128/192/256, and MP3 128/192/320, intersected with nonempty server format and bitrate lists; Original remains first. This is a curated subset, not every server-supported bitrate.
- **Buffering (its own group following Playback):** preload 0/1/2/3 upcoming tracks; temporary stream-cache limit from 10–200 MB in 10 MB steps (20 slider values; change is applied only after Apply); allow preloading on mobile data, disabled when track read-ahead is 0. Offline saved downloads are a separate cache from this temporary stream cache.
- **Downloads:** Wi-Fi-only downloads toggle; offline storage limit choices are decimal 1/2/4/8/16/32/64 GB or unlimited, with current offline bytes used shown in the summary.
- **Appearance:** System/Light/Dark theme; wallpaper color toggle only on Android 12/API 31+; pure-black AMOLED toggle; font choice Downtify classic/System/Google Sans Flex; floating navigation bar toggle; Android per-app Language row only on Android 13/API 33+ (delegates selection to system settings).
- **About:** About Downtify row includes app version and opens About. The separate About surface includes version/build, source, bug-report link, license, terms/disclaimer, and project support links. About/license content is a distinct surface rather than settings preferences.

The persisted settings model also has **library layout** (Grid/List), **library sort** (Recently added, Alphabetical, Artist), and **descending order**. These do not appear on the Settings screen: [LibraryScreen](https://github.com/henriquesebastiao/downtify-android/blob/100be83e49c3250424e6326670a73bff69325b73/app/src/main/kotlin/com/henriquesebastiao/downtify/feature/library/LibraryScreen.kt) exposes layout for non-Songs tabs and a sort bottom sheet for all tabs; the sort sheet offers Ascending/Descending and the three sort modes. Recently added defaults descending; picking a different sort resets to that sort's default direction. Songs are always list layout.

### Connect decision scenarios

1. `GET /api/server/info` is public and is the compatibility/capability source. `product != "Downtify"` is rejected; `api_version > 1` is rejected as too new. The documented contract says refuse newer API versions; this source does not define a lower bound for `api_version` or a minimum semantic server version.
2. On a supported server with `capabilities.password_sign_in=true`, connect proceeds to username/password; with it false or absent, it goes to pairing code. Pairing remains an explicit alternate on the sign-in step. Wrong password/code are distinct; `429 Retry-After` disables retry until countdown ends.
3. A scanned QR's base URL is preferred and its `sid` must equal the server's `server_id`; mismatch is shown as “other server” and no pair request is sent. A discovered server with API version above 1 is filtered from suggestions, but the user can still enter an address and receive the explicit too-new error.
4. Settings refresh probes the paired base URL. Matching server id and valid Downtify response means Connected and updates cached info/name; another server id, non-Downtify response, or too-new server means Different server; network/unreachable errors mean Unreachable. Last-known `/api/server/info` remains cached across launches so capabilities are still available offline.

## iOS implementation evidence

- **Server info and transport (Task 3, initial implementation):** `Downtify/Network/V1/APIClient.swift` normalizes HTTPS-by-default addresses while preserving reverse-proxy paths, requests public `GET /api/server/info`, checks the Downtify product and API version ceiling, and returns typed status, `Retry-After`, compatibility, decode, and transport errors. The default client requires explicit opt-in before sending non-public requests over HTTP. `Downtify/Info.plist` enables ATS local networking only; normal TLS validation remains enabled. Transport errors do not expose the request URL, headers, or underlying URLSession error.
- **Evidence:** `DowntifyTests/APIClientContractTests.swift` covers path normalization, embedded credential/query rejection, server info, product/API compatibility, `Retry-After`, and the no-send-before-consent gate. `DowntifyTests/ConnectionServiceTests.swift` covers QR address/server matching, pairing and password auth contracts, HTTP consent binding, Keychain persistence/replacement/sign-out, and revoked-session checks. `xcodebuild test` on the booted iPhone 18 Pro (iOS 27.0) simulator passed all 42 tests. Bonjour permission prompts and discovery still need a physical-device check; camera UI remains Task 10.
- **Library storage and sync (Task 5, initial implementation):** `Downtify/Data/LibraryDatabase.swift` uses transactional SQLite writes and ordered schema migrations; `LibraryRepository` commits track deltas/tombstones and the cursor/ETag checkpoint together, retries transient failures, and re-fetches after checkpoint conflicts. `LibraryWebSocket` and `LibrarySyncCoordinator` refresh on `library_changed`, resync after reconnect, and cancel work when the app backgrounds or session changes. Cache scope is server plus normalized username, falling back to device ID for older auth responses without a username. The database lives in protected Application Support and is excluded from backup.
- **Evidence:** `DowntifyTests/LibrarySyncTests.swift` covers migration, full/incremental/304 sync, rollback, interrupted and repeated sync, concurrent checkpoints, retry timing, account isolation/persistence, socket refresh and sign-out cancellation. The integrated iPhone 18 Pro (iOS 27.0) simulator suite passed all 42 tests. Real server and physical-device file protection/Bonjour behavior remain unverified.

- **Playback engine and stream resolution (Task 6, initial implementation):** `Downtify/Playback/PlaybackStream.swift` verifies server identity before bearer-authenticated byte-range streaming, binds stream requests to the saved HTTP consent, validates content ranges/ETags and chooses only formats and bitrates supported by both the server and AVFoundation runtime. `PlaybackQueue`, `PlaybackController`, `AVPlaybackEngine`, and `PlaybackSystem` implement duplicate-safe queue editing/restoration, position persistence, shuffle/repeat, audio interruption/route handling, background playback, AirPlay/Bluetooth routing, lock-screen commands, and Now Playing metadata. Opus is offered only when AVFoundation reports Ogg Opus support; otherwise mobile quality defaults to AAC when available.
- **Evidence:** `DowntifyTests/PlaybackTests.swift` exercises queue operations/restoration, capability filtering, server-bound auth, HTTP consent, range validation, original fallback, lifecycle/interruption behavior, ranged WAV playback and Ogg Opus when supported. The integrated iPhone 18 Pro (iOS 27.0) simulator suite passed all 42 tests. Physical-device background/lock-screen, Bluetooth/AirPlay and live-server streaming remain unverified.

- **Playback cache and pretranscode (Task 7):** The app shares a bounded in-memory LRU of 512 KiB stream blocks across playback and optional read-ahead. Entries are isolated by server, account, stream URL and representation validator. The resolver authenticates and probes again before reuse, and streams without strong ETags reuse blocks only within their own resolve. Read-ahead warms the initial block of up to three upcoming unique tracks in queue order, with an opt-in for cellular byte preloading. When byte read-ahead is inactive, a capability-gated HEAD warms the next supported transcode without transferring the audio. The cache defaults to 100 MB with read-ahead off. Read-ahead covers initial blocks during the current app process. Task 8 owns persistent offline media, and Task 17 owns the settings UI. [Mobile client streaming contract](https://github.com/henriquesebastiao/downtify/blob/main/docs/mobile-client-contract.md#5-stream-and-download)
- **Listens and activity (Task 7):** The controller counts forward playback time toward half the track or four minutes. The listen outbox writes protected, account-scoped files before sending, removes a file after successful acknowledgment, and retries through reconnects and relaunch with the original play ID and timestamp. Deduplication after an ambiguous response relies on the server honoring `play_id`. Retries run while the app is executing, including during background playback, and resume when the app runs again. Activity sends online-only start, pause, resume, stop and 30-second playback snapshots with an installation ID. [Mobile client reporting contract](https://github.com/henriquesebastiao/downtify/blob/main/docs/mobile-client-contract.md#8-report-plays)
- **Normalization (Task 7, partial Android parity):** Optional local processing measures decoded RMS and sample peak, derives a gain per track and protects peaks with headroom and a sample ceiling. AVFoundation starts playback while measurement downloads and decodes a temporary copy. The tap starts applying gain after measurement completes and requires a supported Float32 PCM tap format. Streams larger than 20 MB, tracks longer than 15 minutes, and tracks AVAudioFile cannot decode play at their original level. The measurement uses sample peak and RMS. AirPlay, external renderers, and gain at the physical output need device verification. The default remains off. Task 17 owns the settings UI.
- **Task 7 evidence:** Playback tests cover account and quality cache isolation, read-ahead policy, capability-gated HEAD, online activity transitions, an interrupted listen acknowledgment followed by replay of the same persisted request, seek/pause and restart listen tracking, and measured gain and clipping with a decoded WAV fixture. Live-server behavior and physical audio routing remain unverified.

- **Offline downloads (Task 8):** The app uses the versioned track stream with `download=true`, probes size and format with HEAD, and saves verified media under a server, account and device scope in Application Support. HTTPS servers advertising signed URLs can hand off to a background URLSession without putting the pairing token in the transfer. Explicitly approved HTTP and HTTPS without signed URLs use a foreground session that rejects redirects. Completion requires a complete file with matching MIME and length, the same strong ETag when available, and a consistent Content-Range if iOS resumes a transfer. The contract does not publish a content checksum. Local playback prefers the saved AVFoundation asset and does not consult the server for audio bytes. The temporary stream cache and server download jobs have separate state.
- **Recovery and storage:** The app restores last observed progress, reconnects surviving background tasks, and exposes cancel, delete and retry. It checks free capacity and an optional storage limit before committing to another transfer and reports storage write failures. The limit applies to new transfers; it does not evict user-saved files. Wi-Fi-only and storage limits are service settings for the future Settings screen. iOS schedules background requests and cancels them when the app is force quit from the app switcher. After manual relaunch, missing tasks become interrupted and can be retried. A retry starts a new download when iOS did not retain the task; the app does not persist partial data or credential-bearing resume blobs. [Downtify media contract](https://downtify.henriquesebastiao.com/mobile-client-contract/#_5-stream-and-download), [Apple background session lifecycle](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:)).
- **Server queue (Task 8):** Queue jobs and status come from the server queue endpoints. Requesting a server download by link makes a track eligible for library sync. It never creates a local download. Paired devices can read the queue and submit download requests; queue mutations such as pause and deletion require a browser session. Task 15 owns the screens. [Downtify API reference](https://downtify.henriquesebastiao.com/api-reference/#queue).
